# 常见问题

---

## 参赛与环境

**Q1：不具备 GPU 条件能否参赛？**

开发阶段可以。本仓库的示范方案支持任意 OpenAI 兼容的商用 API，队伍自备 key 即可运行，
无需本地 GPU。

正式提交则须为本地部署的开源权重。决赛在断网沙箱中运行，容器无法连接任何外部服务。
验证阶段赛事方将开放云资源，经 AMD 中国开发者平台申请，配额另行公告。

**Q2：开发阶段使用商用 API、临近提交再更换为本地模型是否可行？**

技术上可行，但存在较大风险。商用 API 与本地小模型在输出长度、指令遵循与代码格式稳定性
上差异明显，围绕前者调校的提示词与重试策略，更换到后者之后往往不再适用。

较为稳妥的做法是尽早在本地模型上完成一次完整运行，规模较小亦可，以商用 API 摸清任务
形态，以本地模型确认方案成立。

**Q3：不具备 AMD 显卡与服务器时如何安装 Vivado？**

Vivado 的安装由队伍自行完成，本仓库不提供安装指导。`selftest/` 仅负责定位队伍已安装的
Vivado 并调用，定位失败时明确报错，不会在缺少工具的情况下给出判定结果。

判定所用的仿真与综合不依赖 GPU，亦不要求 AMD 显卡，Vivado 在通用 x86 CPU 上即可运行。
需要注意的是，自 2026.1 起 `xsim` 与 `synth_design` 均须签出授权席位，`xvlog` 与 `xelab` 不
需要。授权的配置方式见 `selftest/env.sh.example`；席位签出失败时判定器报 `LICENSE_ERROR`，该
样本不计入得分。Radeon Cloud 实例上的授权变量设置见仓库 README 开头。

**Q4：能否使用 iverilog 或 Verilator 进行本地自测？**

不建议，本仓库亦不提供该路径。赛事方全流程仅使用 AMD 工具链，本地改用其他仿真器将得到
不一致的判定结果，而不一致的判定较之没有判定更为不利，容易使队伍误认为某类问题已经解决。

**Q5：Windows 环境下脚本能否运行？**

本仓库以 Linux 环境为默认前提。Windows 用户建议在 WSL2 中使用，相关脚本未在原生
Windows 环境下验证。


**Q6：Radeon Cloud 实例是什么配置？模型权重放在哪里？**

| 资源 | 配置 | 说明 |
|---|---|---|
| GPU | 1 张 W7900 系列，48 GB 显存 | 方案仍按单卡 32 GB 设计 |
| CPU / 内存 | 16 核 / 55 GB | `/tmp` 是 4 GB 内存盘，占用的是这 55 GB；EDA 工作目录放 `/var/tmp`，见 README 开头 |
| `/workspace` | 25 GB，持久 | 代码、`env.sh`、模型权重放这里 |
| 其余目录（含 `/root`） | 本地盘，不持久 | 实例重启后清空 |

权重下载到 `/workspace/models`，默认的 `~/.cache/huggingface` 重启即丢。放不下时可以放在
`/workspace` 以外，但每次重启后要重新下载。

实例里 `nproc`、`free` 显示的是物理机的数值，以 16 核 / 55 GB 为准：建议设置
`OMP_NUM_THREADS=16`，同时运行的 Vivado / Vitis 不超过 4 个；内存超过 55 GB 时进程会被终止。

**实例重启会怎样？** 重启后是一个新容器：`/workspace` 保留，其余还原为镜像初始状态，包括
`~/.bashrc` 中的环境变量和 pip 安装的包；推理服务、投题服务与隧道都会停止，重新 `expose`
后网址会变。恢复时依次 `source /workspace/env.sh`、`pip install -r requirements.txt`、
`serve/start.sh`、启动投题服务、重建隧道并报送新网址（见接口契约第六、七节）。评测期间
重启的，中断期间的题按 L0 计（见 Q32），所以评测期间不要重启实例，验证窗口内先演练一次。

**Q7：用镜像自带的 llama.cpp 跑模型，题面稍长就报 `rocBLAS error: Could not initialize Tensile host` 后退出，怎么办？**

启动 `llama-server` 前设置一个环境变量即可：

```bash
export ROCBLAS_TENSILE_LIBPATH=/opt/llamacpp/rocblas/library
/opt/llamacpp/llama-server -m <模型.gguf> --host 127.0.0.1 --port 8000 -ngl 999 -c 24576 --jinja
```

`-c` 不小于题面长度与 16384 之和；`--jinja` 不能省，否则 `manifest.json` 中声明的思考设置
不生效。

## 题集与判定

**Q8：评测题集为何不予公开？**

评测题目由赛事方专门准备，不取自 VerilogEval 等公开数据集，题面格式与仓库里的示例题一致。
题集一经分发即不再具备未见过的性质，而方案在未见题集上的表现才构成泛化能力的真值。

开发阶段建议以 VerilogEval v2 自测，并将实测结果写入设计报告。

**Q9：参考测试台是否提供给参赛智能体？**

不提供。判定 L2 所用的测试台由赛事方掌握，该测试台同时例化参考实现与被测模块并逐拍比对。
参赛智能体仅能获得题面（`prompt`）与模块声明（`interface`）。

如需在生成过程中进行自我验证，须由队伍自行编写测试台。在无法获得参考实现的前提下判断
生成结果是否正确，属于本赛道拟考察的工程问题之一，并非材料上的疏漏，其对应系数为 0.5，
为分级表中跨度最大的一级。

**Q10：L1 至 L2 的分差为何为 0.5，而 L2 至 L3 仅为 0.3？**

L1 到 L2 对应从代码通过工具到行为与参考实现一致，为本 track 中难度最高的一步。L2 到 L3
的跨度则小得多，逐拍比对通过的设计多数已经可综合，其余失败集中于少数不可综合构造。

**Q11：端口名称书写错误会产生何种后果？**

该题计为 L0。参考测试台按具名端口例化被测模块（`.q(q_dut)`），端口改名即等同于缺少一个
端口，`xelab` 详细描述随即失败：

```
ERROR: [VRFC 10-3180] cannot find port 'q' on this module
```

模块名称书写错误同理：

```
ERROR: [VRFC 10-2063] Module <TopModule> not found while processing module instance <dut1>
```

此类错误的代价高于功能实现错误，后者至少可得 L1 的 0.2 分。该规则与软件开发中的一般
经验不同，建议在提示词与技能包中专门处理。示范方案中的 `check_interface()` 即用于此，
以纯文本比较实现，不依赖任何工具。

**Q12：在输出端口上添加 `reg` 是否属于改动接口？**

不属于。`wire`、`reg` 与 `logic` 不构成契约的组成部分，不影响详细描述。将 `output q`
写作 `output reg q` 合法，且在由 `always` 块驱动时通常为必需。

接口契约的组成部分为模块名、端口名、方向与位宽。

**Q13：以 pass@1 而非 pass@5 计分，对稳定性较弱的方案是否构成不公平？**

不构成。稳定性本身就是方案质量的一部分：实际使用中一道题通常只跑一次，要跑五次才能做对一次
的方案并不好用。按 pass@5 计分还会鼓励用重复采样换分数，而采样的耗时已经计入墙钟代价项。

pass@5 与 pass@1 的差值会单独列出，供队伍判断方案的稳定性，不计入总分。

**Q14：五次采样是五次独立运行，还是一次运行可以提交五个候选？**

五次独立运行。每次采样都是一次独立的 `POST /v1/solve` 请求，`nonce` 各不相同，服务每收到
一次请求调用一次 `run.sh`，返回单个 `solution` 字段。接口没有提交多候选的通道。

需要说明的是，在一次调用内部生成多个候选并自行择优不受限制，也正是应当做的：计分取
pass@1，即五次采样系数的均值，提升每一次的期望质量会直接反映在分数上。反过来，以增加
采样次数换取通过率的做法不会提高 pass@1，其时间成本还会计入代价项。

## 模型与方案

**Q15：为何不限制模型参数量？**

参数量难以核查，而显存占用可直接实测。决赛环境单卡显存为 32 GB，超出者无法运行。

参数量与显存占用并不等价：32B 模型在 FP16 下约需 64 GB，无法装载；经 4-bit 量化后约为
18 GB，可以运行；7B 模型在 FP16 下约需 14 GB，可直接使用。在同等显存条件下如何在参数量
与量化精度之间取舍，属于本赛道考察的工程判断之一。

**Q16：选用能力更强的模型是否即可获得高分？**

绝对通过率会相应提高，反映于能力项 30 分。增益项 40 分以该模型的裸跑结果为基线，按归一化
增益计量，即方案补上了基线与满分之间差距的多少。同样的工程水平，换用更强或更弱的模型，
增益分基本不变。模型选择因此只影响能力项，增益项考察的是智能体与技能包本身。

**Q17：能否使用他人已完成微调的硬件专用模型？**

可以，但须在 `MODEL.md` 中声明来源与版本。此类模型公开可得，各队伍均可取用，不构成不
公平。

选用此类模型会抬高能力项；增益项按归一化增益计量，不因模型更强而更高或更低，仍取决于
方案本身。

**Q18：技能包是否必须涉及大模型？**

不作要求。技能包的评价标准在于他人能否复用，与是否调用模型无关。

示范方案中的 `check_interface()` 即为一例，该函数以纯文本方式比较模块头，不调用模型亦
不调用工具，却覆盖了整个 L0 失败类。确定性的校验脚本与结构化的踩坑清单同样计分。

**Q19：以确定性脚本完成接口检查与语法预检，是否属于绕过模型？**

不属于。此类工作本就应当由脚本承担，亦属技能包应有的内容。

判别界线在于产出的设计本身是否由模型生成。以脚本检查模型的输出属于工程实现；以脚本拼接
答案而模型调用不具实质作用，方为评分细则 2.9 所列的第三类情形。

**Q20：能否使用 AMD Ross 的技能与 Vivado MCP 服务器？**

可以用于智能体，不得用于基线。

AMD Ross 的技能以 MIT 许可发布于 https://github.com/Xilinx/ross-ai-assistant ，采用与本仓库
相同的 `SKILL.md` 格式，复制到 `skill/` 后可由 `agent/skills.py` 直接加载。与本 track 相关的
主要是 `vivado-rtl-lint`、`vivado-rtl-elaboration-analysis` 与 `vivado-simulate-rtl`。这几条
技能的操作步骤调用 Vivado MCP 工具，未部署 MCP 时须改写为命令行调用；HLS 系列技能与本 track
无关。引用的技能须在设计报告中注明来源，并说明队伍自行增补的部分，工程质量项评定的是队伍自身
的工作。

Vivado MCP 服务器不预装于官方基础镜像。如需使用，须在队伍的 `Dockerfile` 中自行安装，并确认
其在断网条件下可正常工作；其中的文档检索默认连接 AMD 托管服务，评测环境断网时不可用。按接口
契约第八节，基线不得挂载任何 MCP 服务器。

Ross 官方文档建议配合大上下文的前沿编码模型使用。在 32 GB 显存以内的本地模型上，经 MCP 调用
工具与直接调用命令行孰优孰劣，须由队伍实测判断，相应结论可写入设计报告。

**Q21：`run_baseline.sh` 需要绕过哪些环节？**

须绕过智能体与技能包：提示词仅包含题目本身，单次生成，不重试，不调用工具。

不绕过的部分为推理服务，即同一模型、同一量化方式与同一份上下文配置。基线与方案须在同一
次运行中产出，不接受分次提交，否则增益项的方案与基线不出自同一环境，两者不可比。

**Q22：基线的单次输出上限为 16384 token，是否存在截断风险？能否调整上下文长度？**

`baseline.py` 中的 16384 为单次输出上限（`max_tokens`），与提示词、temperature 同属基线口径，
不得修改；脚本经 SHA-256 核验，改动后增益项不得分。上下文长度由推理服务的 `--max-model-len`
等参数决定，属队伍自定的服务配置，可以调整，须在 `MODEL.md` 中声明。智能体自身的输出上限不受
16384 约束，由 `LLM_MAX_TOKENS` 设置，同样须在 `MODEL.md` 中声明。

两者须相互匹配：服务端上下文长度不得小于题面长度与 16384 之和，否则请求将被推理服务拒绝，基线
产物为空，按 L0 计。HLS-Eval 与 VerilogEval 的题面均在 2k token 以内，上下文长度设为 20k 以
上即可满足。基线单次请求的超时为 840 秒，在 900 秒的单题时限之内。

截断风险存在，其程度取决于模型，推理型模型可能更为明显。选型时宜以 `run_baseline.sh` 在本地
实测。基线中的截断按实际结果计入。

**Q23：思考模式的开关与思考强度怎么设？方案与基线可以各用一套吗？**

不可以，须统一。这类可以逐个请求设置的参数在 `manifest.json` 的 `generation` 段声明，例如
Qwen3 写 `"chat_template_kwargs": {"enable_thinking": false}`，按思考强度控制的模型写
`"reasoning_effort"`。`baseline.py` 读取这一段并随请求发出，方案调用模型时须使用同一套设置，
示范的 `agent/llm.py` 即如此。只认这两项，采样参数、输出上限等写在这里会被忽略。

思考设置对结果的影响是一阶的：开启思考时模型先输出数千 token 的推理过程，更容易撞上输出
上限。方案与基线若各用一套，增益里就混进了一个请求参数的作用，而不只是智能体与技能包的
贡献。

**Q24：经过微调的模型，基线用哪个模型？微调、蒸馏、量化的提升计入增益吗？**

基线用队伍声明的模型，即微调后的模型，不另测基座。微调、蒸馏、量化的提升体现在能力项，
以及工程质量项中对微调方法与效果的说明，不计入增益项。增益项只衡量智能体与技能包在同一
模型、同一推理配置上带来的提升。声明的模型须能以标准对话方式直接回答题目，基线结果明显
异常的进入人工复核。


**Q25：方案的采样参数（temperature、top_p）可以与基线不同吗？**

可以。temperature 0、top_p 1.0 是 `baseline.py` 中的常量，只约束基线。方案如何采样属于
智能体的设计，例如多次采样后择优，不受限制，取值写入 `MODEL.md` 与报告即可。方案与基线须
统一的只有思考设置，见上文「思考模式」一问。

**Q26：方案中除主模型外还用了辅助模型，需要怎样处理？权重必须公开吗？**

辅助模型须在 `MODEL.md` 与 `manifest.json` 中声明名称、基座、参数量、用途、运行位置与显存
占用；单卡 32 GB 的上限包含辅助模型。经过训练或微调的，在 `MODEL.md` 中写明基座、方式、
数据来源与规模。权重随封存版本提交给赛事方用于复现即可，不要求公开发布。辅助模型属于智能体
的组件，基线不含辅助模型，它带来的提升计入增益。详见评分细则 2.12。

**Q27：可以用公开数据集，或开发期由在线 API 生成的数据训练模型吗？**

可以。评测题目不取自公开数据集，用公开数据集训练不受限制；开发期借助在线 API 生成训练数据
同样允许，评测时模型权重在本地、断网运行即可。数据的来源、生成方式与规模须在 `REPORT.md`
中写明。商用 API 的服务条款可能限制「以其输出训练模型」，这一点由队伍自行确认。

## 评测执行

**Q28：正式评测是每题独立调用 `run.sh`，还是一次性提供完整题集？能否跨题并行？**

每题独立调用。赛事方从外部逐题发送 `POST /v1/solve`，服务每收到一次请求调用一次
`run.sh`，产出一份 `solution.v`。完整题集不向参赛队分发，下一题的内容在投递之前无从知晓。

投题在队内严格串行，上一题返回之后才发下一题，跨题并行因此没有可操作的空间。这样安排有
两个原因：接口契约规定一次分发一题，该规定同时构成「无法预置答案」的机制基础；参赛队仅
有单卡，两题同时运行会相互争抢显存与算力，单题墙钟由此失去意义，而墙钟计入代价项。

单题内部的并行不受限制。一次 `run.sh` 调用之内如何组织由参赛队决定，并行生成候选、并行
调用工具验证均可，边界为随请求下发的 `deadline_s`。

**Q29：单题超时如何处理？**

该题按 L0 计。设置墙钟上限的目的在于防止以无限重试换取通过率。

参赛服务应在 `deadline_s` 之前自行停止并返回当前的最好结果，即使为空字符串亦可，而不宜
由赛事方侧触发超时。前者仍存在获得 L1 的可能，后者则计为 L0。

为此建议智能体每生成一版代码就立即写入产物文件，服务到点强制收尾时，交出的就是最近一版。
示范方案即按此实现。

**Q30：除远程投题外，还会直接调用 `run.sh` 吗？超时信号会不会波及常驻服务？**

正式评测只采用远程投题，赛事方只与投题服务交互，不直接调用 `run.sh`，也不向队伍机器
发送任何信号，超时以赛事方侧 `deadline_s + 20` 秒为界。

赛事方按 `Dockerfile` 重建容器、逐题运行保留为退路，仅在远程投题无法进行时启用。届时赛事方
先运行一次 `serve/start.sh`，再逐题调用 `run.sh`，不启动投题服务；超时信号只发给 `run.sh`
所在的进程组，组外进程不受影响。两种方式在一次评测中不会混用。

由此对方案有两点要求。`run.sh` 依赖的常驻进程（推理服务、队伍自己的常驻引擎）一律写进
`serve/start.sh` 并以 `setsid` 拉起，不要由 `run.sh` 在后台带起；`run.sh` 可以只负责投题
与取件、由常驻引擎解题，前提是干净容器中运行 `serve/start.sh` 之后它无需人工介入即可产出
`solution.v`。详见接口契约第八节。

**Q31：平台实例的 1 号进程是 JupyterLab，不回收僵尸进程。评测时也是这样吗？能否自行处理？**

评测时题目投到队伍自己的实例，环境与开发期相同。允许自行处理，范围限于自己的进程树：
示例 `serve/serve_api.py` 已把投题服务设为子进程回收者，每题结束后回收该题的全部进程；
也可以用 `tini -s` 包住投题服务，需在 `Dockerfile` 中自行安装。详见接口契约第十节。

**Q32：服务中途中断后能否重启？**

评测期间不予重启，失败即计为 L0，赛事方不再重投。请在投题前完成健康检查，并确保服务能够
连续处理数百次请求。

**Q33：为何采用墙钟时间而非 token 数计量？**

token 数产生于容器内部，容器外无法可靠观测；且同一模型在不同推理后端下的吞吐可相差数倍，
而后端选择、批处理与 KV cache 管理的调校本身即属本赛道应当考察的工程能力。

**Q34：同时参加两个 track 是否加分？**

不加分。两个 track 独立排名、独立评奖，不作合并计分，最终排名取其中较高者。

建议仅选择其一。两侧的工具链与失败模式差异较大，RTL 侧的主要瓶颈在于语义正确性与时序
语义，HLS 侧则在于可综合性约束与 pragma 作用域。要求两者兼做会明显提高门槛，而对区分度
并无助益。

## 合规

**Q35：哪些行为构成作弊？**

包括以下三类：

- 联网检索。沙箱断网，出流量非零即视为异常
- 硬编码答案。将答案预置于技能包或智能体代码之中
- 绕过模型。以确定性脚本产出结果，模型调用不具实质作用

判定依据为网络出流量、GPU 利用率曲线以及产物与 `trace.jsonl` 的一致性三项，任一项异常
即进入人工复核。经查实者，该 track 成绩作废。

**Q36：智能体中内置固定代码模板是否属于硬编码？**

不属于。提示词模板、代码骨架以及常见的 FSM 写法与复位写法均属正常的技能包内容，本赛道
鼓励此类沉淀。

判别界线在于相关内容是针对某一类问题的通用方法，还是针对某一道具体题目的答案。前者属于
技能，后者属于硬编码。

**Q37：能否使用 Claude Code、Cursor 等工具辅助开发智能体代码？**

可以。本赛道限制的是方案运行时须使用本地开源模型，对开发过程中所用工具不作限制。

按大赛统一要求，须提交大模型协作记录，写入设计报告第 12 节，内容包括：协助开发所用的
大模型与工具名称；设计创新点的来源，哪些来自大模型、哪些来自队伍自己；大模型给出正确建议
与错误建议的地方，错误是怎样发现的；如何验证与判别，最终达成设计。记录错误建议不扣分。

**Q38：演示视频有什么要求？**

在 Radeon Cloud 实例的界面上演示自己的作品，讲解智能体工作流如何构建（服务如何启动、一道题
如何从投题走到产出代码与判级）和设计的创新点。时长与格式按大赛官方要求，随作品在大赛系统中
提交，截止时间与设计报告相同（11 月 4 日 18:00）。
