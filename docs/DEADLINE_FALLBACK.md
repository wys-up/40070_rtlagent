## 1. 时间预算

900 秒是每题从赛事方发出投题到查询到 `done` 的总墙钟，包含排队、模型生成、
工具检查、修复、进程回收和网络传输。不能把每轮生成或每个工具各设成 900 秒，
也不能把契约中的额外 20 秒当成可用解题时间。

以下时间相对于本服务收到题目；外部网络耗时无法由服务精确测量，因此提前返回：

| 时点或阶段 | 默认动作 |
| --- | --- |
| 收题 | 立即返回 HTTP 202；记录单调时钟，重复 nonce 复用原任务 |
| 每次 RTL 生成/修复 | 请求预算最多 240 秒，并从剩余工作预算中留出最多 180 秒供检查使用；该余量最多占剩余工作预算的 35% |
| 编译 / 综合 / 仿真 | 分别最多 120 / 180 / 120 秒，每次都重新受剩余工作预算限制 |
| 模型检查器生成与复核 | 单次请求最多 60 秒，两步与重建重试共享最多 120 秒；不运行未复核的检查器 |
| 已有候选且工作预算不足 60 秒 | 不再开启新一轮 RTL 修复，返回保留候选 |
| 第 870 秒 | agent 的总时间闹钟中断阻塞工作，停止工具，写完 trace 并返回保留候选 |
| 第 880 秒 | 服务端仍未等到退出时，向单题整个进程组发 SIGTERM |
| 最迟第 885 秒 | 若入口仍未退出，发送 SIGKILL；正常退出也清扫残余子进程 |
| 随后最多 3 秒 | 回收本题进程组内的孤儿/僵尸子进程 |
| 第 900 秒之前 | 读取已落盘结果，完成临时目录清理并发布 `done`，为每 2 秒一次的外部查询与传输留出余量 |

第 870 / 880 秒分别来自 `deadline_s - 30` 与 `deadline_s - 20`。
排队时间直接扣除，输入文件准备后再次计算剩余时间。
不足 20 秒的排队任务直接发布空结果；查询接口无需等待前一个任务结束才能报告它已过期。
闹钟和预算使用 `time.monotonic()`，不会因系统墙钟校准而延长。
trace 的 `ts` 仍使用 Unix 时间戳。

### 模型调用耗时口径

RTL 生成、checker 生成和 checker 复核的请求失败现在各写一条
`tool=llm,event=error,rc=1`，使用单调时钟记录 `elapsed_s`；checker 同时标记
`purpose` 和 `attempt`。失败不虚构 token 用量，也不冒充一条模型响应。
checker 的 start 事件记录本次 timeout，成功响应保留 finish_reason。

开发评测摘要保留原有 `llm_calls` / `llm_wall_s` 为成功返回请求的次数/耗时；
新增 `llm_failed_calls`、`llm_timed_failures`、`llm_failed_wall_s`，以及成功与
已记录失败等待相加的 `llm_recorded_wall_s`。它们均不能代替 `agent.wall_s`。
旧日志的部分 checker 超时只出现在 selftest.invalid，无法从新增字段补出耗时；
进程被硬中止而没有终结事件的调用也不完整。因此不将旧批次重新估算成精确模型总耗时，
agent 与独立 judge 的墙钟仍分别记录。

240 秒等单次上限用于限制请求等待；HTTP 库的读取超时不等于严格的整段传输墙钟上限。
Linux agent 的总时间闹钟与服务端独立进程监督共同约束整题。
磁盘卡死、内核不可中断等待和网络中断仍可能越过预算，不能承诺任何故障下均有有效得分。

## 2. 兜底结果如何选择

1. 先剥离思考段并抽取完整 RTL。没有完整 `module` / `endmodule` 配对的输出不进入候选池。
2. 接口检查失败的候选不保存。评测接口字段为空时，沿用从题面端口表取接口的已有实现。
3. 候选按接口、语义、编译、综合和独立功能自检的证据逐级保留。
   每次更优时立即通过临时文件和 `os.replace()` 原子写入 `solution.v`，
   较差的新候选不覆盖旧结果。
4. 生成失败时，已有候选直接返回；尚无候选且仍有预算时可在最多五轮内再次生成。
   这是 agent 内部重试；赛事投题本身不要求重投。
5. 信号中断或异常退出时，保留此前已写出的文件；没有可用候选则返回 `solution: ""`。
   复用输出目录时先清空旧答案，避免把上一题产物当成本题答案。
6. 服务端记录异常退出或强制超时。强杀造成的最后一条不完整 JSONL 会被丢弃，
   其前面的完整调用记录与服务事件仍返回。

检查证据不足的候选可能只达到较低判级，也可能功能错误。自建检查器通过不能证明
通过官方测试；trace 不会把未验证候选标记成 `accept`。

## 3. 基线与两种评测入口

`baseline.py` 和 `run_baseline.sh` 保持原样，不添加工具、技能、重试或 agent 兜底。
HTTP 的进程时限、空串结果与异常记录对 agent / baseline 一致。
基线自身单次请求上限仍为原版的 840 秒；建议明确设置 `MODEL_NAME`，
避免它为了选择模型再次请求 `/models`。Dockerfile 已设置该值。

Linux 上直接运行 `run.sh` 也会在总预算减 30 秒后触发 agent 闹钟，
无需依赖 HTTP 服务。容器重建时赛事方的进程组超时监督仍是最后一层保护。
Vivado / xsim 继承单题进程组，常驻模型仍由 `serve/start.sh` 通过 `setsid` 独立启动。

不要在比赛配置中设置 `MODEL_API_KEY`：原版基线客户端不发送模型鉴权头，
启用推理服务器鉴权会导致基线失败。对外投题端点仍必须设置 `FPGACHINA_TOKEN`。

## 4. 本次发现并修复的问题

| 问题 | 影响 | 修复 |
| --- | --- | --- |
| 生成调用默认可等待 600 秒，缺少检查器共享预算 | 第一轮后修复时间不足 | RTL 调用限 240 秒；检查器生成/复核限 60 秒并共享预算 |
| agent 只在循环间检查预算 | 正在阻塞的调用无法主动停 | Linux 总时间闹钟，服务端独立进程组监督 |
| 原服务预留 10 秒，同时还可能等 5 秒 TERM 和 5 秒回收 | 几乎没有取回与查询余量 | 服务预留 20 秒，agent 预留至少 30 秒，回收最多 3 秒 |
| 等待中的任务只有 worker 取到后才能变成 done | 前题阻塞时，排队过期任务继续挂起 | 查询时也发布排队过期结果 |
| 预算使用系统墙钟 | 校时可能延长或提前时限 | 用单调时钟计算预算与 elapsed |
| 截断代码或错误接口也可能先被保存 | 超时时返回残缺或错误接口 | 完整模块检查；接口通过后才进入候选池 |
| 异常时 done 事件把已有答案字节数记成 0 | trace 与真实产物不一致 | 读取已保存答案的实际文件大小 |
| Vivado 工具另开会话 | 可能逃逸单题进程组，强杀后占资源 | 工具继承单题进程组；单工具超时仅清理其后代树 |
| 自检 xelab 未带 timescale | DUT 与测试台混合 timescale 可能拒绝展开 | 显式设置与自检测试台相同的 `1ns/1ps` |
| Dockerfile 未 COPY baseline.py | 干净重建后基线入口找不到文件 | 补充打包原版基线文件 |
| Docker 临时目录默认 /tmp | 平台 4 GB 内存盘可能写满 | 默认使用 `/var/tmp/agent` 与 `/var/tmp/eda`，按需创建目录 |
| 健康检查未配置后端也默认 mock ready | 模型未启动却可能报告就绪 | 要求显式后端配置，检查 worker 存活及入口文件存在 |
| rocm-smi 使用率被按字节换算 | 显存占用可能错误报为 0 | 使用 VRAM 内存信息 CSV 的已用字节列 |

已检查并保留：三个端点鉴权、异步响应、task_id 原样返回、nonce 去重、
agent / baseline 共用服务配置、空 interface 的题面解析、JSONL trace、
模型服务与投题服务的环回绑定默认值，以及常驻进程的 setsid 启动。
`API_CONTRACT.md` 与原版基线文件未作修改。
